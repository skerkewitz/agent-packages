# Javadoc for Java and Gosu Source

## Scope

Accept a Java or Gosu package name, one source file, or a list of source files. Supported files are Java (`.java`) and Gosu (`.gs`, `.gsx`). Resolve a package against the current project's declared source roots and include files in that package; include subpackages only when requested. If the package exists in multiple source roots (for example, production and test roots), or the intended files cannot otherwise be identified, ask which root or files to use. Do not silently substitute tests, neighboring packages, or another language's files. Do not edit generated code unless the user explicitly includes it. Follow the repository's applicable instructions and existing documentation conventions.

## Workflow

1. Identify the requested files and inspect their code, existing documentation, relevant interfaces or superclasses, tests, and nearby call sites as needed to establish observable behavior. For Gosu, inspect enhancement declarations and property accessors where relevant. Keep the work confined to the requested scope.
2. Document each type, constructor, and **every declared method/function**, including private, package-private, protected, public, static, and overridden members. In Gosu, include functions and properties; explain getter/setter behavior and document each accessor when their contracts differ. Include a short explanation for each instance field, even when private. For Java, document record components as well. Preserve correct existing documentation and improve it only where it misses a material part of the contract. Do not replace meaningful documentation with generic text.
3. Give each method or function a concise, high-level summary of its purpose and important observable effects without narrating the implementation. Write for a mid-level developer who may not know this module. Distinguish what callers must supply (preconditions) from what the member ensures (postconditions). Describe constraints such as accepted nulls, value ranges, units, ordering, state requirements, return nullability or emptiness, mutations, and failure cases **when the code or established contract supports them**. For nullable parameters and optional values that affect behavior, explain the observable outcome when they are absent where it is material, such as whether the member does nothing, leaves state unchanged, applies a default, omits a value, returns `null`, or throws. When a guard prevents a mutation, describe the resulting state accurately; do not imply a field is null if the member merely leaves it unchanged. If an important contract remains uncertain after checking local evidence, ask rather than inventing a guarantee.
4. Use the documentation syntax and tags supported by the target language and project tooling. Put the summary first; use `@param` for parameters, `@return` for non-void methods/functions, and `@throws` for documented failures. Document type parameters where applicable. Make nullability and constraints explicit in the relevant tags. Use code and link tags only where supported and useful. Use `{@inheritDoc}` only when inherited documentation adequately explains the implementation's contract; otherwise add the missing specifics. For Java record components, use the appropriate `@param` tags on the record type. Avoid redundant tags that merely restate names or types.
5. Add a short code example only when it clarifies a non-obvious input, output, or workflow; write the example in the source language and keep it consistent with the actual API. Write all new documentation in English, with readable wrapping and syntax accepted by the relevant Java or Gosu tooling. Do not change runtime behavior, signatures, or visibility just to document them.
6. Review coverage of all requested files, including private helpers, properties/accessors, and instance fields. Run the project's relevant Javadoc or Gosu documentation check, documentation lint, or narrow compile check if available; fix documentation errors introduced by the edits. Report any contracts that could not be established and any validation that could not be run.

## Writing Standard

Prefer precise, compact statements such as "Returns `null` when no matching entry exists" or "Requires a positive timeout in milliseconds" when verified. For a Gosu property, state whether it is readable, writable, or both, and document meaningful getter and setter behavior without duplicating the same contract. Format multiline block documentation consistently: align `/**` with the declaration; indent content lines and the closing `*/` one additional space; align every content and closing `*` with the first `*` in `/**`. Write blank lines as ` *`. Avoid unsupported promises such as "never returns null," speculative exception lists, implementation walkthroughs, repeated boilerplate, and examples that obscure a simple contract. Documentation should let a reader understand what a member is for and how to use it without reading its body.
